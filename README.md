# 偏见试验场 / arenaofbias

一个半娱乐、半测评的 AI 作品对比网站：让人看作品、凭自己的判断选择，再从大量选择中观察哪些 AI 的输出更受欢迎。

**首先让人愿意一直玩、愿意分享，其次让积累下来的主观结果具有参考价值。**

本文描述项目的长期定位、核心玩法与产品原则，不是当前功能清单或开发任务。文中的长期方向不代表已经实现。

## 仓库分工与开发入口

| 仓库 | 维护范围 |
| --- | --- |
| `arenaofbias`（本仓库） | 主站前端、竞技场、题库、榜单、分享与纸 / 墨主题。 |
| [ArenaGalleri](https://github.com/wsnxxxs/ArenaGalleri) | 独立 Gallery 前端及消费端构建工具。 |
| [arenaofbias-server](https://github.com/kme7kme7-prog/arenaofbias-server) | 两站共用 API、账号、投票、社区投稿和管理后台；唯一写业务数据库的服务。 |
| `arenaofbias-data` | 私有题目、作品和注册表，以及收录与不可变数据包发布。 |

主站与 Gallery 分别维护前端，通过共享后端和数据包对接。本仓 `server/` 与 `/admin.html` 保留迁移前实现；当前管理入口为 `https://api.arenaofbias.icu/admin/`。接手状态见 [HANDOFF.md](HANDOFF.md)，当前行为见 [docs/PRODUCT.md](docs/PRODUCT.md)，本地联调与发布见 [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md)。

开发环境需要 Node ≥ 22.12。安装依赖后运行 `npm run dev:web`；将共享后端启动在本机 3000 端口，或用 `PORT` 指定 Vite 代理的后端端口。运行 `npm run typecheck` 检查类型、`npm run build` 构建静态站点。`npm run dev` 启动的本仓旧服务仅用于旧实现验证，不具备当前共享后端的完整接口。

## 为什么做这个项目

AI 生成的东西最终是给人使用、阅读和观看的。除了客观指标，人是否喜欢、是否愿意继续读、是否愿意使用，同样重要。

这个项目希望用尽可能简单的参与方式收集这些判断。用户不必懂模型原理，也不必填写复杂评分表：在同一任务的两份作品之间，选择自己更喜欢的一边即可。

我们想回答的是「哪个 AI 的写作更受参与者喜爱」「哪个 AI 做的网页更受欢迎」这类问题。结果反映特定题目、生成条件和参与人群下的主观偏好，不宣称存在适用于所有人的唯一最强模型。偏好不同是这个项目要呈现的信息，不是需要消除的错误。

## 为谁而做

项目希望同时服务不同用户，并通过不同模式承接他们的需求：

- **AI 爱好者**：发现模型之间的差异，参与有趣的比较与讨论。资源有限时优先服务这类用户。
- **普通体验者**：不需要专业知识，也能随手玩几轮，发现值得分享的作品和意外结果。
- **想挑选 AI 工具的人**：把大家的选择作为参考，寻找更符合自己需求和偏好的模型。
- **模型开发者**：观察人们对输出的实际反应，了解模型在不同任务中的受欢迎程度。

不要求所有人都把榜单当作权威。有人只是来玩，有人愿意参考结果，两者都符合项目目标。

## 核心玩法

基本循环是：**进入一道题 → 查看同题的两份作品 → 选择左边或右边 → 查看揭晓结果 → 继续下一场或分享。**

提示词是比较的共同背景，作品是用户判断的主体，模型身份是揭晓和统计的一部分。盲测时先看作品再揭晓身份，降低品牌印象对选择的影响。

用户侧的核心操作保持简单。题库组织、作品抽取、对手匹配和评分汇总的复杂度应由系统承担，不转化成每轮必填的问卷。

## 首页与玩法结构

首页的职责是「进入」：要抓住眼球，可以隆重，不追求轻量；3D 与动效元素可以作为氛围背景，但必须弱于主按钮、不抢视觉重心。视觉重心落在进入玩法菜单的入口上——一个明确的主按钮，点进去是玩法菜单页，菜单列出当前开放的玩法，点进具体玩法后才开始评测。

玩法分层（名称为暂定）：

- **正式测评**：面向有资格参与者的严格盲测，资格标记在账号上（资格制后续实现）。任何环节都不揭示模型名称，也没有评论区——选择只汇入偏好数据。
- **娱乐测评**：面向所有人的主要玩法。做出选择之后揭晓模型身份，并开放评论区讨论。
- **特别赛**：常驻或轮换的独立玩法（如「鹈鹕大乱斗」），各自拥有独立页面与规则。

不同模式共享「看作品、做选择」的基本交互，但不共用同一套揭示与讨论规则，也不意味着必须共用同一套计分规则。娱乐特别赛是否影响正式排名，需要单独明确。

## 题库与作品从哪里来

题库以项目维护者组织和维护为主。作品可以由系统统一调用模型生成，也可以由维护者按约定条件手动生成后上传。

题库（题目档案）允许更丰富的陈列方式，例如空间化的档案陈列；但检索效率优先：陈列不能过大到妨碍浏览，并且必须始终提供快速检索入口。

长期允许指定的可信参与者贡献作品，例如由维护者邀请的资深用户群体。这不等于默认向所有用户开放不受筛选的上传。

一道题可以对应多个模型的结果，同一个模型也可以在同一道题下积累多个输出。比较的对象是具体作品；模型层面的结果则来自多份作品、多次对局的积累，避免把一次发挥直接等同于模型的长期水平。

题目、模型、作品和对局应在概念上区分清楚：

- **题目**：共同的提示词、任务要求和生成条件。
- **模型**：参与生成的 AI 身份及版本。
- **作品**：模型在指定条件下的一次输出；特别赛也可能包含人类作品。
- **对局**：选取两份作品进行一次比较，收集用户的选择。

## 怎样理解公平比较

常规测评以相同提示词和统一生成条件为基础，比较模型在这些条件下实际生成的结果。

允许使用工具，也认可工具使用和多轮修改本身属于 AI 的能力。关键是参赛模型获得一致的工具权限、修改机会和适用规则，而不是要求它们必须执行完全一样的操作。具体工具、轮次和资源限制，应在对应测评规则中明确。

系统生成与手动上传都应遵循该场比较的条件，并能说明作品如何产生。不同条件的作品能否比较、是否单独设赛道，应明确决定，不能默默混入同一排名。

统一提示词能统一任务，但不会自动解决题目覆盖、输出偶然性、重复投票或样本不足等问题。未来的匹配与统计设计应处理这些问题，同时保持前台参与简单。

## 排名要表达什么

长期方向是通过成对比较，为模型形成类似 Elo 的评分与匹配机制，并按写作、网页等任务类别呈现偏好榜单。正式测评与娱乐测评的选择汇入同一份偏好榜，但榜单必须能切换为「只看正式」；特别赛独立成榜，不混入主榜（见决策 026）。更细的能力维度或雷达图，需要有对应题目和足够数据支撑。

Elo 是候选的统计与匹配路线，不是已经确定的完整算法。具体计分方式、跨题汇总和特别赛规则仍需设计。

展示排名时，应让用户看到它的依据与不确定性，例如参与比较次数、涉及题目数，以及是否仍处于暂定或试评阶段。少量胜场不应被呈现为稳定结论。

榜单提供参考，不替用户决定喜好。某个模型受到多数参与者欢迎，不意味着每个人都应喜欢它，也不意味着它在所有任务上都更强。

## 体验与设计原则

- **好玩优先**：让人愿意继续参与和分享，是首要的产品成功标准；榜单的参考价值来自持续积累。
- **低负担参与**：左右选择是主要动作，避免每轮增加复杂判断和填写成本。
- **作品优先**：用户需要看清作品，长内容需要合适的阅读与展示节奏。
- **游戏式体验**：重视入场、聚焦、选择与揭晓的动效衔接，让网页具有游戏感。动效应服务观看与反馈，避免遮挡作品或制造无意义等待。
- **有视觉性格**：避免套用泛化的极简 AI 产品模板；具体配色、布局与细节可以迭代，不把某个临时视觉方案当作长期定位。
- **尊重主观差异**：不把少数派选择当作错误，不把主观排名包装成绝对能力结论。

## 什么算成功

人们愿意主动进来玩，愿意继续下一场，也愿意把有趣的题目、作品和揭晓结果分享出去。

在这个基础上，积累的结果能为愿意参考它的人提供一定帮助，例如挑选写作模型或网页生成工具。项目不以让所有人相信同一份榜单为前提。
