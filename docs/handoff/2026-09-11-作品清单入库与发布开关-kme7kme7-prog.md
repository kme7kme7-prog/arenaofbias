## 本轮目标

后台内容管理体系的地基：把作品名单从「编译进代码的 JSON」迁进 SQLite works 表，带发布开关与可扩展的迁移机制。本轮**不做后台页面**（整版后台方案已与用户讨论定稿，见决策 040 关联段）。

## 背景与决策

- 后台方案讨论定稿：同仓库双应用、管理员标记站内账号、宝塔批量传文件 + 后台文件浏览器登记、发布开关（用户拍板「带发布开关的那种」）、页面全做功能可占位但要诚实标注未开放。
- 用户明确缩小本轮范围：「先不做后台，把那个数据库做了」，并要求「别写太死，以后可能会多加一些表的字段」。
- 数据库选型：继续 SQLite（现有库），不引入 MySQL——演示规模用不上，备份与运维成本白增（已向用户摆明并认可）。
- 决策 040 已录入 `docs/DECISIONS.md`。

## 改动

- `lib/works-roster.json`：升级为**完整作品清单**（身份 + content 整包入 JSON，002 两篇小说从 arena.ts 的 `stories` 搬入）。
- `lib/arena.ts`：删除 `stories` 与 `contents` 表，`modelResults` 直接是 roster 的类型化引用，启动时校验每条作品的身份字段与 content.kind（漏配即报错）；`Story` 类型显式化。
- `server/index.js`：
  - 新增 `MIGRATIONS` 数组（`PRAGMA user_version` 驱动，启动时按序应用幂等 SQL）；迁移 001 建 works 表（id / prompt_id / model_id / model_name / title / is_demo / content JSON / published 默认 0 / created_at）+ works_prompt 索引，表空时把 roster 种入并全部置已发布（不覆盖已有行）。
  - 新增 `GET /api/works`：公开返回已发布作品（按登记时间升序），content 为 JSON 字符串。
  - B2 票面核对改查 works 表：rid 必须存在、已发布、非 demo、属本题、与 mid 一致（逻辑与决策 039 相同，数据源从 JSON 文件升级为库）。
- `lib/works.ts`（新建）：`fetchWorks`（逐行解析、坏行跳过、空表视为失败）、`loadWorks`/`getWorksState`/`subscribeWorks` 小型 store、`currentWorks()`（未就绪返回内置 `modelResults`）。
- `src/main.tsx`：启动即 `loadWorks()`，`Routes` 用 `useSyncExternalStore` 订阅就绪后重渲染。
- `lib/placeholder.ts`：`currentResults()`（占位关闭时）改为返回 `currentWorks()`——真实数据以远端清单为准。
- `app/prompt-preview.tsx`：演示样例查找从内置 `resultsForPrompt` 改为 `currentResultsForPrompt`（统一口径）。
- 验证脚本：`validate-placeholder.mjs` / `validate-leaderboard.mjs` 拼合模块补 works.ts 转译注入（含 fetch 占位 shim）；`validate-votes.mjs` 扩至 11 项（新增 GET /api/works 种子回归）。
- 文档：DECISIONS 040、ARCHITECTURE（代码地图 / API 面 / 扩充步骤 / 技术备注）、PRODUCT（数据归属）、HANDOFF。
