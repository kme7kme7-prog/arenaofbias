## 029 · 改动效前先建对照工具：check 断言 + reference 对照页，按 A/B/C 分层

- 日期：2026-09-10 ｜ 状态：生效
- 决定：改任何动效前先把当前行为冻进对照工具再改。分级：A 级「状态机型」（涉及路由/数据/可中断状态）配 `scripts/check-*.mjs` 不变量断言 + `reference/*-review.html` 调参页；B 级页面装饰动画只进对照页；C 级 hover/focus 微动效不建工具。断言只锁不随设计重排而碎的不变量（层挂 body、盖满才换路由、只动 transform、中断从当前值接续、结束必清理），节奏/文案/缓动属设计参数由对照页调、不入断言

## 040 · 作品清单入库（works 表 + 发布开关），后台体系的地基

- 日期：2026-09-11 ｜ 状态：生效
- 决定：作品从「编译进代码的 JSON」迁移进 SQLite works 表：`content` 存 ResultContent 同构 JSON（加字段不动表结构）、`published` 发布开关（新登记默认未发布，前端只见已发布）、`PRAGMA user_version` 驱动的启动迁移（首启动把 `lib/works-roster.json` 种入空表，全部置已发布，不覆盖已有行）。前端新增 `GET /api/works` 拉取已发布清单（`lib/works.ts`），拉到则以远端为准、拉不到回退内置花名册——站点行为不因加载失败而变化；投票 B2 校验改查 works 表（只认已发布）。数据库继续用 SQLite，不引入 MySQL 等新服务。
- 理由：后台内容管理（登记作品→点发布→前台即刻生效）的前提是作品名单在库里而非代码里；用户明确要求表结构可扩展（迁移机制 + JSON content 即为预留）。
- 被否方案：起新项目做独立后台系统（数据/账号/运维三重复成本，单人维护不划算）——已定同仓库双应用（管理后台 UI 后续轮次再做）；MySQL（演示规模用不上，备份与运维成本白增）。
- 关联：后台整版方案（管理员标记账号、宝塔传文件 + 后台文件浏览器登记、仪表盘、占位页面）已在 2026-09-11 对话与用户讨论定稿，本轮只落地地基；后续轮次实施。
- 来源：本轮用户拍板「先不做后台 把那个数据库做了」并要求「别写太死 以后可能会多加一些表的字段」
